# Warehouse ERP

Modular monolith on .NET 10 / EF Core 10.0.13 / SQL Server: one application, one database, one `ErpDbContext`, and modules that only talk to each other through their Contracts.

Migration 01 (Organization and Catalog) is generated by `dotnet ef` (`src/WarehouseERP.Persistence/Migrations`) and verified on SQL Server LocalDB.

## Structure

```
src/
  WarehouseERP.Api/                  host: wires persistence and modules (Program.cs)
  WarehouseERP.Persistence/          ErpDbContext over every module's configurations, migrations
  BuildingBlocks/
    WarehouseERP.SharedKernel/       MasterEntity and its temporal mapping
  Modules/
    Organization/
      WarehouseERP.Organization/            Domain, Application, Persistence (configurations)
      WarehouseERP.Organization.Contracts/  IWarehouseDirectory, WarehouseType
    Catalog/
      WarehouseERP.Catalog/                 Domain, Application, Persistence (configurations)
      WarehouseERP.Catalog.Contracts/       IProductCatalog, ProductType, TrackingMode
tests/
  WarehouseERP.Tests/                integration tests on a throwaway LocalDB database
  WarehouseERP.ArchitectureTests/    module boundary rules
```

Module rules, enforced by `WarehouseERP.ArchitectureTests`:

- A module references only `WarehouseERP.SharedKernel` and `*.Contracts` projects, never another module, `Persistence` or `Api`.
- Contracts and the shared kernel reference no project.
- Each module owns its entity configurations and schema, and reaches its own tables through `DbContext.Set<T>()`. `Persistence` registers `ErpDbContext` as `DbContext`, so a posting that spans modules stays in one transaction.
- Foreign keys between modules are configured in `ErpDbContext`, the only place that sees every module.
- A new module: `src/Modules/<Name>/WarehouseERP.<Name>` + `WarehouseERP.<Name>.Contracts`, an `Add<Name>Module()` call in `Program.cs`, its configurations applied in `ErpDbContext`, and a line in `ModuleBoundaryTests.Host_wires_the_known_modules`.

Package versions live in `Directory.Packages.props`; shared build settings in `Directory.Build.props`.

## Included

- 13 master-data entities: Organization (company, branch, warehouse, location) and Catalog (category, unit, product, product unit, barcode, external item code, tax code, tax rate, product tax assignment).
- Creation commands that keep cross-row invariants: `WarehouseCommands` (warehouse + DEFAULT location) and `ProductCommands` (product + base unit row).
- Temporal tables: all Organization and Catalog master tables; history tables under `history` schema.
- No operational AuditLog tables, no stock tables, no manufacturing entities in Migration 01.
- `Product.BaseUnitId` **only**, `ProductUnit` has no `IsBaseUnit`; creation service inserts its row with `ConversionFactor=1`.
- `WarehouseLocation` has no `IsFrozen`; later counting state belongs to active `StockCountScope`.

## Prerequisites

- .NET 10 SDK; SQL Server 2019+ or LocalDB.
- `dotnet-ef` 10.0.13 is a local tool (`dotnet-tools.json`): run `dotnet tool restore` once, then call it as `dotnet dotnet-ef`.
- Set `ERP_SQL_CONNECTION` to your *development* database. On the development laptop use **LocalDB**, not `Server=.`: the default SQL Server instance there belongs to another live system.
- Never commit secrets or production credentials.

PowerShell, from the repository root:

```powershell
$env:ERP_SQL_CONNECTION = 'Server=(localdb)\MSSQLLocalDB;Database=WarehouseERP_Dev;Trusted_Connection=True;TrustServerCertificate=True'
dotnet tool restore
dotnet build WarehouseERP.slnx

$p = 'src/WarehouseERP.Persistence/WarehouseERP.Persistence.csproj'

# Inspect the SQL before applying it.
dotnet dotnet-ef migrations script --idempotent --project $p --startup-project $p -o Migration01_OrganizationCatalog.sql
dotnet dotnet-ef database update --project $p --startup-project $p

# A new migration later:
dotnet dotnet-ef migrations add <Name> --project $p --startup-project $p --output-dir Migrations
```

A design-time factory reads `ERP_SQL_CONNECTION`; no connection string is embedded in source code. The API reads `ConnectionStrings:Erp`, set to LocalDB in `appsettings.Development.json`.

## Running the API

```powershell
cd src/WarehouseERP.Api
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet run
```

`GET /api/health` answers `{"status":"ok"}`. In Development the host validates the whole DI graph at startup.

## Tests

```powershell
dotnet test WarehouseERP.slnx
```

- `WarehouseERP.Tests`: each run creates its own LocalDB database (`WarehouseERP_Tests_<guid>`), applies the migrations and drops it at the end. Set `ERP_TEST_SQL_SERVER` to point the tests at another SQL Server instance.
- `WarehouseERP.ArchitectureTests`: fails when a module references another module, `Persistence` or `Api`.

## Constraints worth noting

1. **One DEFAULT location**: SQL filtered unique index prevents more than one default per warehouse. `WarehouseCommands.CreateWarehouseAsync` ensures there is one *at creation*. The existence guarantee requires prohibiting arbitrary direct writes and never deactivating the only default location; a DB trigger or stored procedure is an option for stronger enforcement.
2. **Base unit**: `Product.BaseUnitId` is canonical. `ProductCommands.CreateProductAsync` writes its matching `ProductUnit` row at factor 1 in one SaveChanges transaction. The FK alone cannot enforce that the matching row exists or remains factor 1; require a protected application command and validation on updates/deletes. Do not edit `BaseUnitId` after inventory starts.
3. **Temporal master history**: `ValidFrom/ValidTo` are SQL Server-generated; `history.*History` versions master changes. `CreatedByUserId` / `UpdatedByUserId` are attribution columns, not an operational AuditLog.
4. **No cascade deletes**, master data uses `IsActive` for retirement. Avoid deleting rows with references or history.
5. **Tax periods**: `[EffectiveFrom, EffectiveTo)`; DB checks valid bounds and same-date uniqueness, but *overlapping ranges* need serialized application validation (e.g. applock) until a stronger DB mechanism is implemented.
6. **Category cycles**: single-row self-parent prevented by CHECK; deeper category hierarchy loops require application validation.
7. **Barcodes**: global unique barcode; data normalization and GS1 checksum if applicable belong in application services.
8. **EF client sequential GUIDs**: no `Guid.NewGuid()` for keys when adding entities; let EF assign values via `.ValueGeneratedOnAdd()`.
9. **Temporal table migration**: generated migration / database script must be inspected for history schema, SQL Server permissions, check constraints, FK delete actions, indexes and concurrency columns.
10. **ExternalItemCode**: optional `ProductUnitId` references a unit **belonging to the same Product** via a composite FK.

## Deliberately postponed (NOT in Migration 01)

- `ProductWarehouseStock`, `StockBalance`, `StockMovements`, `StockReservation`, `StockCountScope`.
- `AuditLog` only for operational actions; `Outbox/Inbox` and document numbering.
- Per-`DocumentType` approval policy: `RequiresApproval` decided by configuration, with external-module documents permitted to post `Draft -> Posted` when authorized and validated.
- Inventory costing uses `decimal(19,8)` for unit prices, and will update both `TotalQuantity` and `TotalValue` on issues.
- Negative-stock corrections / over-reserved alerting: do **not** add `CHECK (ReservedQuantity <= OnHandSellable)` to Migration 02.
- Reconciliation between sellable `StockBalance` rows and `ProductWarehouseStock`, excluding Transit warehouses.

## Quality gate before deploy

- Build and generate migration; inspect generated SQL.
- `dotnet test` covers: temporal history on edit, RowVersion conflicts, inactive inserts, delete restrictions, duplicate SKU/barcode, selling Transit warehouses (service and CHECK), a second DEFAULT location, the warehouse and product creation commands, EGS codes pointing at another product's unit, and both module contracts resolved through DI.
- Still to cover once their services exist: tax period overlaps and multi-level category cycles.
- Supply user context when executing mutations; authorization and detailed business commands are future work.
